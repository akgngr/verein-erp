   309→## 5. BUSINESS RULES
   310→
   311→1. **Meeting number**: `TOP-<year>-<sequence padded to 3 digits>` (pads grow beyond 999). `year` = calendar year of `meetingDate`. Sequence is per year across all meeting types. Generated atomically in a `prisma.$transaction` with `MeetingCounter` upsert (`kind: MEETING`, `lastSeq: { increment: 1 }`), the same technique and `P2002` retry (max 3) as Phase 1. The number is immutable: it is not editable and stays unchanged even if `meetingDate` later moves to another year (`// KARAR:` note).
   312→2. **Decision number**: `<year>/<sequence>` (example `2026/7`), `year` = year of the meeting's date, sequence per year across all meetings (`MeetingCounter` kind `DECISION`), generated atomically inside the transaction that creates the decision. Deleting a decision never frees its number (gaps are acceptable).
   313→3. **Status workflow** (`constants.ts` holds the transition map; `meeting-guards.ts` enforces it on the server):
   314→
   315→   | From | To | Required permission | Extra conditions |
   316→   |---|---|---|---|
   317→   | PLANNED | HELD | update | none |
   318→   | PLANNED | CANCELLED | update | none |
   319→   | CANCELLED | PLANNED | update | none |
   320→   | HELD | APPROVED | approve | at least 1 agenda item and at least 1 attendee with attendance PRESENT |
   321→   | APPROVED | HELD (reopen) | approve | mandatory `reason` (5–500 chars), stored in the audit record |
   322→
   323→   Any other transition is rejected. Approving sets `approvedAt`, `approvedById`, `approvedByLabel`. Reopening clears them. If `quorumRequired` is set and not reached, approval is still allowed but the UI confirmation dialog must warn: "Toplantı yeter sayısı sağlanmamış. Yine de onaylamak istiyor musunuz?".
   324→4. **Locking** (`assertMeetingEditable(meeting, scope)`, called by EVERY action; UI hiding is not sufficient):
   325→   - Scope `content` (meeting fields, agenda, discussion notes, attendees, decisions, action item add/edit/delete): allowed only when status is PLANNED or HELD.
   326→   - Scope `actionStatus` (marking an action item DONE/OPEN): allowed in every status except when the meeting is soft-deleted (follow-up continues after approval).
   327→   - Scope `files` (upload): allowed in every status except soft-deleted (signed scans are uploaded after approval). File deletion: when status is APPROVED it requires the `delete` permission (ADMIN); otherwise `update`.
   328→   - Soft-deleted meetings accept no operation and are treated as not found.
   329→   - Locked-state violations return an `ActionResult` error such as "Onaylanmış toplantı tutanağı düzenlenemez. Önce yeniden açın.".
   330→5. **Delete**: `delete` permission (ADMIN) only. Soft delete (`deletedAt`, `deletedById`, `deletedByLabel`). Not allowed while status is APPROVED (must be reopened first). A deleted meeting disappears from lists, search, stats, action-item list and the dashboard. Its numbers are not reused. Files stay on disk.
   331→6. **Optimistic concurrency**: only for the main meeting edit form (hidden `updatedAt`, mismatch error "Bu kayıt başka biri tarafından değiştirildi. Sayfayı yenileyip tekrar deneyin."). Child records (agenda, attendees, decisions, action items) use last-write-wins (`// KARAR:` note).
   332→7. **Agenda**: `position` is 1-based and contiguous. Add appends at the end. Move up/down swaps positions inside a transaction. Delete renumbers the remaining items in the same transaction (decisions linked to the deleted item keep existing with `agendaItemId = null`). The planned content (`description`) and the minutes text (`discussion`) are separate fields; discussion is saved by its own action `updateAgendaDiscussion` and is editable in PLANNED and HELD.
   333→8. **Attendees**:
   334→   - Add internal attendees from `listActiveUserOptions()` (can add several at once). A user can be added once per meeting. Add external guests by free-text name (role forced to `GUEST` by default, but may be set to MEMBER).
   335→   - At most one CHAIRPERSON and one SECRETARY per meeting; assigning a second returns an error "Bu toplantıda zaten bir başkan var." / "…sekreter var.".
   336→   - `attendance` and `role` can be changed per attendee (inline select). "Tümünü katıldı işaretle" sets all INVITED attendees to PRESENT.
   337→   - Quorum (`services/quorum.ts`): `presentCount` = attendees with attendance PRESENT; if `quorumRequired` is set, `reached = presentCount >= quorumRequired`. Shown in `QuorumBanner`: "Toplantı yeter sayısı sağlandı (X/Y)" (green) or "Toplantı yeter sayısı sağlanmadı (X/Y)" (amber); no banner when `quorumRequired` is null.
   338→9. **Decisions**: `text`, `result`, optional `agendaItemId` (must belong to the same meeting), optional votes. Votes are all-or-nothing in the form: either all three fields empty (stored null) or all three numbers (0–1000, empty treated as 0 once any is filled). Add/edit/delete only in PLANNED or HELD.
   339→10. **Action items**: `description`, optional assignee, optional `dueDate`, optional `decisionId` (must belong to the same meeting). Assignee is EITHER an active user (`assigneeId` + `assigneeLabel`) OR free-text name (`assigneeId = null`, `assigneeLabel` = text) OR none. Setting status DONE sets `completedAt`, `completedById`, `completedByLabel`; reopening clears them. Overdue = `dueDate` before today (Europe/Berlin) and status OPEN.
   340→11. **Copy from previous meeting** (create form, optional `copyFromMeetingId`): the new meeting receives copies of the source's attendees (role kept, attendance reset to INVITED, user attendees only if the user is still active, guests kept) and agenda items (title and description only; discussion NOT copied). Decisions and action items are never copied. The source must be a non-deleted meeting of the same type.
   341→12. **Validation (zod)**:
   342→    - Meeting: `type` (required, create only), `title` (3–200), `meetingDate` (required), `startTime` (optional, `HH:mm` regex), `endTime` (optional, requires `startTime`, must be later than it), `location` (≤200), `quorumRequired` (optional integer 1–500), `description` (≤2000), `copyFromMeetingId` (create only, optional), `updatedAt` (update only).
   343→    - Agenda item: `title` (2–200), `description` (≤2000), `discussion` (≤10000).
   344→    - Attendee: guest `name` (2–120), `note` (≤200).
   345→    - Decision: `text` (3–3000), `votes*` (0–1000).
   346→    - Action item: `description` (3–1000), free-text assignee name (2–120).
   347→    - Empty strings become `null`; all text is trimmed. Free text is plain text: render with `whitespace-pre-wrap`, never as HTML.

   397→## 8. SHARED FILE HANDLING REFACTOR (`shared/files/`)
   398→
   399→Goal: both `documents` and `meetings` use the same hardened file code.
   400→- `file-types.ts`: central registry mapping extension → allowed MIME types → magic-byte signature check. Include everything Phase 1 supported (pdf, jpg/jpeg, png, doc, docx, xls, xlsx, odt, ods, txt) plus `pptx` (zip signature). SVG, HTML, JS and executable types stay forbidden.
   401→- `validation.ts`: `validateUpload({ file, allowedExtensions, maxBytes })`: extension in the caller's allowed subset, client MIME matches extension, signature check passes (same rules as Phase 1).
   402→- `storage.ts`: `saveFile`, `openReadStream`, `removeFile`, `resolveSafePath(relativePath)` (path-traversal protection: resolved path must start with `UPLOAD_DIR`). Paths are always built from DB-stored `storagePath`; `storedName = crypto.randomUUID() + lowercase extension`; original file names are sanitized (control characters and path separators removed) and only stored in the DB.
   403→- `http.ts`: `parseSingleFileUpload(request)` (multipart, field `file`) and `buildDownloadResponse({ stream, originalName, mimeType, inline })` implementing the Phase 1 header rules: `X-Content-Type-Options: nosniff`, `Cache-Control: private, no-store`, RFC 5987 `Content-Disposition` with `filename*=UTF-8''...`; `inline` honored only for pdf/jpg/png, everything else always `attachment`.
   404→- Refactor `documents` services/handlers to use these functions. Keep Phase 1 behavior identical: its allowed-extension subset, 20 MB default limit (`MAX_UPLOAD_MB`), 10 files per document, existing stored paths and DB records. Do not touch Phase 1 data.
   405→- `meetings` uses the same allowed extensions as above including `pptx`, `MAX_UPLOAD_MB`, 20 files per meeting, storage path `meetings/<year>/<meetingId>/<storedName>`.
   406→- Upload handler (`POST /api/meetings/[id]/files`): session (401 JSON) → `meetings.update` permission (403 JSON) → meeting exists and not deleted → file-limit and validation → write to disk → `MeetingFile` row → audit `FILE_UPLOAD` → JSON `{ ok: true, file }` or `{ ok: false, error }`. On any failure remove the already-written file. Download handler (`GET /api/meetings/files/[fileId]`): session + `meetings.view`, file and parent meeting not deleted, `?inline=1` rule as above. Handlers never redirect.
